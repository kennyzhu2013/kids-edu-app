## 1. 结论

方向不用推翻，但先前那份「扁平知识点 + 把掌握度和 GamePlugin 放进第一步」的方案需要改。附件和现有产品是对齐的：在保留当前课程、关卡、游戏和小芽体验的前提下，先建设统一的知识点和学习数据基础，再谈掌握度、复习、今日计划和家长报告，最后才考虑 AI。不要推倒重做，也不要在本期上 CMS、新的游戏引擎，或把语音方案从 Piper 换成云端服务。

需要改的核心有三处：

1. **知识怎么分层：** 用「学科 → 课程专题 → 知识点」三级结构，替换原先扁平的约 20～30 条标签（如 `math.count.1-5`）。
2. **先做哪一层、做到多深：** 不要一次实施任务书里的全部 V1.1 能力。按 Sprint 0 → 1 → 2 → 3 推进；教育内容先拿一门数学课做完整试点，再扩展到其他学科。
3. **哪些必须提前、哪些必须后置：** 演示凭证隔离和隐私说明提前到 Sprint 1；GamePlugin、掌握度公式、复习计划和报告升级后置到 Sprint 2、Sprint 3。

建议的下一步是先做 **Sprint 0**：只审查 `d1f84de` 源码并写出改造影响和可执行任务拆解，先不改业务代码、不执行数据库迁移。本文中的模型细节，仍应在 Sprint 0 对照真实代码后再微调。

当前产品已是可完整体验的 MVP，改造应增量叠加，而不是另起炉灶。

| 现状 | 说明 |

## 3. 需要坚持的设计原则

1. **课程是教学组织单位，知识点是学习和评估单位，游戏是可服务多个知识点的活动载体。** 三者不要混在一起。例如「认识数字 1～10」是课程专题（如 MA01），「认识数字 1-5」才是知识点，「数一数冲关」挂到知识点上，而不是写死在某一门课里。
2. **年龄不是第四级目录。** 继续使用现有 A / B / C。每个知识点配置各年龄段学习目标（`ageTargets`），目标是参考性发展目标，不是强制升级门槛。
3. **前置关系用多对多，不要只用单个 `parentId`。** 真实学习过程会有跨专题依赖。建议独立的 `KnowledgeDependency`，关系类型为 `prerequisite` / `related` / `extension`。`courseId` 只表示该知识点在目录树上的所属专题，不能代替依赖关系。
4. **三级目录只负责知识分类。** 不要把所有 Lesson、Question、Game、Assessment 都强行塞进目录树；它们挂在知识点之下，课程体系保持稳定，教学内容可继续扩充。
5. **现有 Pack / Level 先保留。** Pack 不等于 Course 的一一对应（例如 `math-starter` 可能同时覆盖 MA01、MA02、MA04）。不要为了目录整洁一次性拆掉关卡播放器。
6. **先数据，后 AI。** 没有知识点、题目、错因和学习行为数据，后续个性化就没有依据。大模型不得直接决定掌握度；AI 生成内容必须先校验、再审核，才能进入正式课程库。
7. **增量迁移，禁止破坏性操作。** 用 Prisma Migration；不删除原有课程和游戏数据；不为迁目录而大规模搬迁代码；不为引入新框架而重写已有成熟功能。

## 4. 相对先前方案，需要修改的地方

先前方案（扁平知识点目录 + 第一步就建掌握度表）与附件对照后，建议按下面调整。

| 项目 | 先前方案 | 修订后 |
|---|---|---|
| 知识点模型 | 扁平标签，约 20～30 条，颗粒度偏粗，没有「课程专题」层 | 三级结构：学科 → 课程专题 → 知识点；正式规划为七大学科、约 45 个专题 |
| 学科范围 | 沿用产品四科入口思考 | 规划目录用七个模块；产品界面暂时仍是四个 Tab，不做七个入口 |
| 实施打包 | 第一步就包含知识点、事件原始次数，并容易把掌握度、GamePlugin 捆进来；任务书更是把内容引擎、题目、插件、掌握度、复习、报告都算进 V1.1 | 严格按 Sprint 0 → 1 → 2 → 3；任务书中的能力要拆开，不要一次做完 |
| 内容迁移范围 | 容易理解成「现有课程全部迁入新模型」 | 先建目录，不一次录入全部知识点；先映射已有中英数和生活数学及 5 个游戏；内容引擎以一门数学课做完整试点后再推广 |
| Question | 任务书把步骤整体升级为独立题目模型 | 不要大拆现有 Level 步骤；Question 仅作为数学课试点，验证后再推广 |
| GamePlugin | 任务书列为 P0，且容易设计过重 | 放到 Sprint 2；只用现有 React 组件加一层很薄的适配，统一生命周期和结果上报；不引入 Phaser 或其他新引擎 |
| 掌握度 / 复习 / 报告 | 任务书列为 P0/P1 且与内容建设写在同一期 | 放到 Sprint 3；Sprint 1 最多只记录原始次数，不算掌握度 |
| 跟读与评分 | 任务书要求答案和得分必须服务端校验、不能信任客户端 | 点选、拖拽、排序等客观题走服务端校验；跟读仍在设备上评分，且录音不上传，故这类分数不能当成服务端最终可信分。事件中保留 `no_hearing` |
| 演示凭证与隐私 | 任务书主要放在 Sprint 4 发布检查 | 演示 PIN、验证码、后台令牌的生产隔离，以及隐私和监护人同意说明，提前到 Sprint 1 |
| 内存回退 | 本地开发仍可用 | 明确：仅限本地/开发；生产必须有数据库，禁止用内存数据冒充持久化 |

## 5. 课程目录与产品映射

### 5.1 正式规划目录

正式一级学科采用七个模块，约 45 个课程专题。这是规划数量，不是必须立即上线的内容量。每个专题可逐步建设 5～15 个三级知识点。

| 一级学科 | 建议专题数 | 首期优先级 | 产品侧对应 |
|---|---|---|---|
| 中文启蒙 | 6 | P0 | 语言 Tab |
| 英语启蒙 | 7 | P0 | 英语 Tab |
| 数学启蒙 | 8 | P0 | 数学 Tab（含生活数学） |
| 科学探索与认知 | 8 | P1 | 认知 Tab |
| 健康与生活 | 6 | P1 | 洗手等生活习惯内容；暂挂现有相关关卡/游戏 |
| 社交与情绪 | 5 | P1 | 本期只建目录，不作为新入口 |
| 艺术与创造 | 5 | P2 | 本期只建目录，不作为新入口 |
| **合计** | **45** |  | 界面暂不拆成七个 Tab |

映射关系补充：认知 Tab 对应「科学探索与认知」，不要继续使用早期六分法里单独的「认知科学」作为正式学科名。社交情绪、艺术创造先留目录，避免产品信息架构和大改版绑在一起。

### 5.2 数学专题编码需要先定一套

规划材料内部有两套写法，落地前必须选定，避免 fixtures 和数据库各写各的：

- 分领域表曾把数学写成 **MA08 时间认知 + MA09 生活数学**（共 9 个专题）。
- 完整示例树把二者合并为 **MA08 时间与生活数学**，第八节正式目录也写数学为 8 个专题。

**建议：** 现有独立内容包 `math-life`（生活数学）不要和「时间认知」混编成同一个专题。优先保留「生活数学」作为单独专题，即使总数因此变成 46 而不是 45。具体编码（仍用 MA09，或改为数学下的独立代码）在 Sprint 1 写入课程规范，并全库统一。

同样需要避免的混淆：「认识数字 1～10」是专题名称，不是知识点。知识点应落到「认识数字 1-5」「认识数字 6-10」等更细条目。年龄目标应写在这些细知识点上，而不是写在专题上。

### 5.3 现有内容首批映射

首期只映射已经存在的课程和游戏，不批量录入全部知识点。

| 现有内容 | 建议归属 |
|---|---|
| `lang-starter`（中文起步） | 中文启蒙：语言理解与表达、汉字、儿歌/绘本等已有关卡对应的专题 |
| `eng-starter`（英语起步） | 英语启蒙：字母、基础词汇、日常表达、听力口语等已有关卡对应的专题 |
| `math-starter`（数学起步） | 可能跨 MA01 数字认知、MA02 数量与数感、MA04 图形认知等，按关卡逐条打知识点，不要 1:1 绑死一个专题 |
| `math-life`（生活数学） | 数学启蒙中的生活数学专题 |
| `life-starter`（生活起步，含洗手等） | 健康与生活 |
| 数一数冲关 | 数字认知 / 数量与数感 |
| 形状拼合 | 图形认知 |
| 颜色配对 | 先按关卡实际考察点挂到颜色或分类相关知识点，不要因为游戏名叫颜色就写死到艺术学科 |
| 找动物 | 科学探索或中英词汇中的动物类知识点，按关卡语言和目标挂载 |
| 习惯排序 | 健康与生活（生活习惯） |

拼音、20 以内运算可以出现在目录里，但 **不得做成 3～4 岁（年龄段 A）的必修目标**。3～4 岁数学以数量感知和简单比较为主。

内容建设分批：

1. **第一批：** 把现有中文、英语、数学（含生活数学）课程和 5 个游戏全部关联到统一知识点。
2. **第二批：** 科学探索与认知、健康与生活，重点提高现有游戏的可复用性。
3. **第三批：** 社交与情绪、艺术与创造，补综合素养类课程。

这套目录还需要经过儿童教育专业人员审核，尤其是年龄目标和评估标准。技术侧先按此落地结构，不把未审核的目标写成能力鉴定。

## 6. 数据与运行时改造要点

### 6.1 Prisma 增量增加，而不是重建

Sprint 1 优先增加：

- `KnowledgePoint`（含 `code`、`subjectId`、所属专题、`ageTargets`、难度、状态、排序、版本等）
- `CourseKnowledgePoint`（课程专题与知识点关联）
- `KnowledgeDependency`（多对多前置 / 相关 / 扩展）
- 关卡步骤和游戏配置增加 `knowledgePointIds`
- 如需会话级追踪，可为后续事件预留 `sessionId`，但完整 `LearningSession` 可放到 Sprint 2

Sprint 2 增加：

- `LearningEvent`（含 `childId`、`sessionId`、事件类型、知识点、正误、时长、错因、幂等键、UTC 时间）
- 如有必要，再补 `LearningSession`

Sprint 3 增加：

- `KnowledgeMastery`（规则计算结果；数据不足标「待评估」）
- `ReviewPlan`（1 / 3 / 7 / 14 天的初始间隔，可按数据校准）

`Question` 只在数学课试点中引入，不作为 Sprint 1 全量必交付。`Achievement`、`LearningRecommendation`、`ContentVersion`、`Conversation` 均非本期必做。

现有 `Progress`、`TodayPlan`、`GameQuota` 继续工作，新模型与之并存，待数据口径稳定后再考虑是否收敛。

### 6.2 学习事件

事件类型以任务书的封闭列表为起点：`learning_started`、`lesson_started`、`lesson_completed`、`question_answered`、`question_failed`、`hint_requested`、`game_started`、`game_completed`、`review_completed`、`learning_paused`。

必须额外保留 **`no_hearing`（没听清）**：这不是做错，不得记入错误次数，也不得掉星，更不得据此降低掌握度。

硬性要求：

- 事件必须关联正确的儿童档案，服务端校验当前用户是否有权操作该档案。
- 写入支持幂等（可沿用现有 Progress 的 `clientEventId` 思路）。
- 时间统一按 UTC 存储，展示时再转到用户时区。
- 追加式记录，不覆盖历史行为。
- 不采集非必要的儿童隐私；跟读音频默认不上传、不长期保存。
- 重要事件不应因页面关闭而丢失（可先本地队列，待有网络再补报）。

错因初期只用有限枚举：`concept_error`、`recognition_error`、`operation_error`、`listening_error`、`attention_error`、`unknown_error`。不得仅凭答错就判定注意力不集中；无法可靠判断时记 `unknown_error`。

关于「服务端最终判分」：客观题（点选、拖拽、排序、匹配等）必须服务端校验。跟读评分依赖设备端识别，且录音不上传，因此只能作为带来源标记的参考分，不能写成服务端权威掌握度依据。界面也不得宣称「识别一定在本地完成」——Chrome 等环境下，Web Speech 可能把音频发到系统或厂商服务。

### 6.3 掌握度（仅 Sprint 3）

先用规则算法，不引入机器学习。任务书建议的工程估计为：

\[
M = 0.4A + 0.25C + 0.2R + 0.15D
\]

其中 A 为近期正确率，C 为连续正确表现，R 为间隔复习表现，D 为不同题型表现，变量归一化到 0～100。

| 分数 | 状态 | 推荐动作 |
|---|---|---|
| 数据不足 | 待评估 | 不判「未掌握」，继续收集练习 |
| 0～39 | 未掌握 | 重新讲解 |
| 40～59 | 学习中 | 简单练习 |
| 60～79 | 基本掌握 | 巩固练习 |
| 80～100 | 熟练 | 安排间隔复习 |

这是工程初始规则，不是儿童能力诊断标准。单次答错不得大幅降分；报告在数据不足时显示「数据不足」，不生成虚假结论，也不对儿童做医学或心理诊断。

### 6.4 游戏插件（仅 Sprint 2，保持轻量）

五款现有游戏保留，通过很薄的 `GamePlugin` 适配器统一：初始化、开始、暂停、恢复、提交、取结果、销毁。统一 `GameResult` 和学习事件上报。新增一种游戏不应修改课程主流程；异常退出不得记为完成。

本期不引入 Phaser、Blockly 或其他游戏框架。只有未来出现复杂动画或强实时交互时，再单独评估。

### Sprint 1：三级目录、打标与安全基线

- 落地七大学科目录和专题编码（含数学生活专题的最终编码决定）。
- Prisma 增量增加知识点、专题关联、依赖关系；现有 Pack / Level 保留。
- 为已有中英数、生活数学关卡和 5 个游戏打上 `knowledgePointIds`。
- 用一门数学课做完整试点：目录、打标、（可选）Question、客观题服务端校验、用统一方式加载，验证后再推广。
- 演示家长锁、短信验证码、后台令牌在生产环境隔离；补齐隐私和监护人同意说明。
- 未配置数据库时开发环境仍可用内存，但生产路径必须拒绝「无库冒充已持久化」。

验收：现有页面和关卡不回退；已有内容能按知识点查询；数学试点课可走通；生产配置不再暴露开发默认密钥。

### Sprint 2：薄插件 + 学习事件

- 五款游戏接入统一生命周期和结果上报。
- 建设 LearningEvent（含会话、错因、幂等、按儿童档案鉴权、`no_hearing`）。
- 关卡播放器同步上报关键步骤事件。

验收：课程和游戏都能记录完整学习过程；重复提交不重复计算；异常退出不误记完成。

### Sprint 3：掌握度、复习、今日计划与报告

- 规则法掌握度；数据不足标「待评估」。
- 错题与 1/3/7/14 天间隔复习；同一天同一知识点不重复生成有效复习任务。
- 今日计划改为优先复习和薄弱点，再安排新知识和兴趣游戏；每日任务量可配，未完成不给儿童压力。
- 升级家长报告：学习习惯、知识掌握、成长趋势、学习建议；必须有真实数据支撑。

验收：学习 → 评估 → 复习 → 报告可以闭环；儿童端和家长端展示口径区分开。

### Sprint 4：稳定性与发布（在 1～3 完成之后）

数据迁移、权限、游戏兼容、事件幂等、页面回归、性能、部署与安全检查。现有功能不回退。W5 广告/会员、W8 提审与落地页、真实登录/支付、原生工程，仍单独决策，不并入本方案自动开工。

## 8. 附件之间的冲突与裁决

| 冲突点 | 材料怎么说 | 本方案怎么定 |
|---|---|---|
| 一级学科数量 | 任务书内容树写中/数/英/科学/认知共 5 项；规划文先写 6 大领域，后改为正式 7 模块 | 以规划文第八节的七个模块为准 |
| 知识点从属与前置 | 任务书 KnowledgePoint 含 `parentId` 和 `prerequisiteIds`；规划文明确反对单一 `parentId`，要求 `KnowledgeDependency` | 采用多对多依赖；所属专题用关联表或 `courseId`，不用 `parentId` 表达前置 |
| 是否一次迁完所有课程 | 任务书 Sprint 1 / 验收写「现有课程全部接入」；额外建议要求先迁一门数学课 | 先映射已有内容标签，完整引擎能力以一门数学课试点，再推广 |
| 任务书把 Question、GamePlugin、掌握度都标 P0 | 额外建议不要一次实施所有任务，游戏不要过度设计 | 按 Sprint 拆分优先级，见第 4、7 节 |
| 数学 MA08 / MA09 | 规划文自身不一致 | 见 5.2，保留生活数学独立专题 |
| 事件列表没有「没听清」 | 任务书封闭列表未包含 | 保留并正式纳入事件规范 |
| 「服务端最终得分」与跟读实现 | 任务书禁止前端计算最终可信分；当前跟读不上传音频 | 客观题服务端权威；跟读分为参考分并标明来源 |

## 10. 给后续开发的执行约束

1. 先审查源码，再改代码；每个任务独立提交和验证。
2. 优先复用已有组件、关卡播放器和数据模型。
3. 新业务模型必须有 TypeScript 类型和 Zod 校验；高频查询字段结构化存储，JSON 只用于差异化配置。
4. 所有儿童数据读写都要做档案权限校验。
5. 保持现有视觉风格、小芽角色和交互，不借改造做一次 UI 大改版。
6. 每项改动输出：修改/新增文件、数据库与 API 变更、兼容性说明、测试结果、未完成事项和风险。
